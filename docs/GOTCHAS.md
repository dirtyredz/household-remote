# Gotchas

- The original plan is historical; its monorepo/Views/helper instructions and verification commands are superseded by CLAUDE.md and VERIFY.md.
- Pair each phone independently. Shared client name does not imply shared tokens. Two-phone coexistence needs physical acceptance.
- REST information is unauthenticated. Never trust a discovered IP as identity; WSS pins are keyed by MAC. A changed certificate requires re-pair while watching the correct TV.
- Multicast may be filtered; manual IP is supported. Wake depends on TV/network settings and a usable Wi-Fi broadcast interface.
- Offline does not prove off, and standby has no acknowledgment: the remote channel reports no panel power state. "On · connected" means a usable session; "Standby sent" means the socket accepted one KEY_POWER frame. Do not disconnect right after standby (cancelling the socket can drop the queued frame). Wake still depends on the TV's network-standby/Wi-Fi wake settings and a usable Wi-Fi broadcast interface.
- "Reconnecting…" and "TV unavailable — check Wi-Fi or Wake" are transport states: the saved pairing is intact, and the fix is Wi-Fi, Wake or Reconnect, never re-pairing. Only a typed `TrustChanged`/`PairingRequired`/`Denied` Offline needs the attended re-pair. Recovery is bounded to 60 s per outage and foreground-only; it does not keep a backgrounded app connected, and it is deliberately disabled for the drop after standby (call `RemoteSession.suppressRecovery()` before any future deliberate-disconnect key).
- "Phone not on Wi-Fi" means no network with the Wi-Fi transport exists; it does not prove the TV's LAN is reachable. Wi-Fi joined but with mobile data still the default network (an unvalidated or "no internet" Wi-Fi, or a VPN) can leave unbound sockets on mobile data, so the TV shows Reconnecting/unavailable rather than the Wi-Fi hint. The monitor runs only while foregrounded and starts from a default-network guess that its callback corrects within moments.
- The remote never scrolls (owner ruling). New controls must come out of the D-pad's flexible height or the compact layout rule in `RemoteScreen.compactRemote`; keep `RemoteScreenTest`'s fit checks (360x640 at 1.0/1.3, 411x891 at 1.3) passing.
- The heartbeat proves the socket, not the TV: `send` true means OkHttp queued the frame. A key sent just before an undetected half-open drop can be lost and is never retried. The 15 s ping is a proposed default; confirm Samsung tolerates it during phone acceptance.
- `res/values/colors.xml`, `drawable/ic_remote.xml` and the launcher XML are byte-checked outputs of `src/android/icons/generate-icons.mjs`; put other colors in `values/remote_colors.xml`.
- Home-bar positions and delays drift. Recalibrate while watching; cancel immediately if navigation is wrong.
- No phone is attached during implementation. Keystore, Android installer, multicast permissions, actual TV response and latency need device acceptance.
- Gradle's shared daemon registry crosses worktrees: another checkout's `gradlew --stop` can stop a single-use build here. VERIFY.md isolates the registry under `.tmp/gradle-daemon` while retaining the shared dependency cache. Still wait for other builds and never issue global daemon stops. The installed SDK command-line tools emit an SDK XML v4/v3 compatibility warning; no SDK download is needed to address app source failures.

- Household inventory belongs only in ignored `config/household.local.json` or `.tmp/`; examples are fictional. The privacy gate rejects the household subnet and non-placeholder 1Password references.
- Windows `local.properties` needs an escaped drive colon (`sdk.dir=C\:/...`); an unescaped colon can build successfully but fails release lint. Prefer `ANDROID_HOME` when setting up a new checkout. Lint can cache this error without tracking a local-properties edit; use `--rerun-tasks` on the fast gate after fixing it.
